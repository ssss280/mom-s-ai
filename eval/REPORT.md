# 联网搜索评测报告（`web_search.py`）

> **⚠️ 2026-09-21 返工说明（先读这段）**
>
> 本报告第 2~6 节是**第一轮**（1.5.0）的结论。那一轮用"先跑完原始实现、再跑完新实现"
> 的方式对比，得出"总分 43.1 → 85~95"。改用**交替 A/B**（同一时刻逐题交替跑两份实现）
> 重测后，这个结论**不可复现**：搜索引擎可用性随时间剧烈变化，把"引擎可用性差异"
> 当成了"代码差异"。实际在同一时间窗口下，1.5.0 的实现明显更差（判据全中 5/25 对 18/25、
> 中位延迟 12.1s 对 1.2s，首条常是「2026年放假安排」这类跑题结果）。
>
> 返工内容与新的回归结论见 **`CHANGELOG.md` 的 1.2.0 条目**与本文第 9 节。
> **跨时间比较请一律用交替 A/B，不要用本报告第 2~6 节的单次分数做前后对比。**

本报告记录"生成随机测试集 → 实测打分 → 定位问题 → 优化 → 用同一测试集回归"的完整过程。
所有数字都来自 `eval/runs/` 里落盘的原始记录，可复跑复核。

## 1. 怎么测的

| 环节 | 做法 | 文件 |
| --- | --- | --- |
| 题库 | 25 道中文/英文真实问法，每题带**客观判据**（关键词分组 + 期望域名），覆盖事实/时效/价格/技术/长尾/追问/对抗错误前提 | `eval/cases_bank.json` |
| 抽题 | `--seed` 固定则抽出的题目固定；也可 `--all` 跑完整题库 | `eval/harness.py` |
| 执行 | 真实调用 `web_search.search()`（含跳转还原、正文抓取），**不 mock 网络** | 同上 |
| 评分 | 判据全中率 / 基本中率 / 平均覆盖 / 空结果率 / 首条命中率 / 平均可信结果数 / 延迟分位 / 链接可打开率 / 正文抓取率 / 来源域名数 | 同上 |
| 落盘 | `testset.json`（题目）、`records.json`（每题结果）、`links.json`（链接体检）、`metrics.json`（指标+总分） | `eval/runs/<名字>/` |
| 打分函数调参 | 359 条标注结果（含 8 条"权威域但跑题"对抗负样本），算 AUC / 精确率 / 召回率 / F1 | `eval/tuning/` |

评分不是让模型"感觉好不好"，而是**可核对的事实**：例如"2025 年诺贝尔文学奖得主"必须出现在结果里，
"北京中轴线列入世界遗产"必须命中 `unesco.org` 或官方来源。总分是六项加权：

```
命中正确性 35 + 非空率 20 + 链接有效性 15 + 正文可读 10 + 延迟 10 + 引擎均衡 10 = 100
```

## 2. 基线（优化前）：43.1 / 100

| 指标 | 基线 |
| --- | --- |
| 总分 | **43.1** |
| 空结果率 | **60%**（25 题里 15 题直接回"没查到"） |
| 判据全中率 | 4% |
| 判据平均覆盖 | 0.237 |
| 平均结果数 | 1.16 条 |
| 唯一贡献引擎 | 只有 `bing`，且只喂进 10 条 |
| 首条命中率 | 90%（唯一亮点：能出结果时首条通常是对的） |
| 延迟 P50 / P90 | 2.06s / 2.84s |

15 道空结果题的错误信息高度一致：**"试了 N 种查询词，10~20 条都被判为不相关"**。
也就是说引擎"有返回"，但结果全被判为无关。

## 3. 定位到的真问题

### 3.1 `www.bing.com` 给爬虫返回整页"诱饵结果"（最严重，也最隐蔽）

引擎探针（`.bld/probe_*.py`）实测：

| 查询 | `www.bing.com/search?q=...&setlang=zh-CN` 返回的前几条 |
| --- | --- |
| 香港国际秋季灯饰展 2026 | Lady Gaga — Wikipedia / Microsoft Support / 韩国棒球联赛 |
| ChatSight | 一堆物联网文章（ASME） |
| 香港国际秋季灯饰展 | 法语 Facebook 帮助页 |

关键在于**页面结构完全正常**：有 10 个合法的 `<li class="b_algo">`，解析器不会报错，
所以"搜到了"这个判断是假的——喂给模型的是一整页假事实。

对比同一时刻的其它入口：

| 入口 | 同一查询的结果质量 |
| --- | --- |
| `www.bing.com/search`（原实现） | 全跑题（诱饵页） |
| `cn.bing.com/search?mkt=zh-CN` | 命中（灯饰展/会展中心/天气页） |
| `www.bing.com/news/search?format=RSS` | 命中，且 25 题里 17 题直接达标 |

补充证据：`www.bing.com/search?q=...&mkt=zh-CN` 也是命中的，**带 `mkt` 才正常** ——
说明这是缺市场参数时被喂了诱饵页。

### 3.2 其它引擎当时的状态（实测，非猜测）

| 引擎 | 现象 |
| --- | --- |
| `so360` | 6.4KB「访问异常页面」，零结果 |
| `sogou` | 5.4KB `antispider` 验证页 |
| `duckduckgo` | `html.duckduckgo.com` 返回 `anomaly.js?cc=botnet` 挑战页（**时通时不通**） |
| `baidu` | 有时 17 条好结果，有时直接 `百度安全验证` |

所以基线"只有 bing 可用"其实是"只有 bing 在返回东西，而它返回的是假的"。

### 3.3 打分函数不是瓶颈（用数据排除）

在 359 条标注结果上（含 8 条对抗负样本）：

| 规则 | AUC | t=0.30 时 P / R |
| --- | --- | --- |
| 现行 bigram 覆盖率打分 | **0.985** | 0.991 / 0.905 |

打分函数的排序能力已经很好，**卡点在取数**：给它诱饵页，它只能把诱饵页判低分，
于是"全被判为不相关" → 空结果。这条结论决定了优化方向不是重写打分，而是修取数。

## 4. 优化内容

1. **修 Bing 入口**：主力换 `cn.bing.com` + `mkt=zh-CN`；新增官方**资讯 RSS** 源；
   `www.bing.com` 降级为最后兜底。
2. **搜索引擎按实测抗压程度重排为 4 批**（前一批不够数才升级）：
   `bing_cn+bing_news` → `duckduckgo+wikipedia` → `sogou+baidu` → `bing_web+so360`。
3. **英文查询换顺序**：实测 `cn.bing` 对纯英文技术问题不看查询词（搜 asyncio 返回 Python 官网首页），
   而 stackoverflow/官方文档只有 DuckDuckGo 与英文维基给得出来。
4. **升级条件更严**：够 3 条但最高分 < 0.45（只是"沾边"）继续升级。
5. **跨批次按分数取最优**，而不是后一批覆盖前一批。
6. **修 3 个 bug**：追问句被削成空查询词、引擎冷却跨查询把自己饿死、
   传输层故障的引擎被反复重试（DuckDuckGo 曾一轮被调 10 次全超时）。
7. **打分加"来源是否对味"**：查询词出现在域名里 +0.10、权威站 +0.06；阈值 0.3→0.28、兜底 0.2→0.15。

## 5. 回归结果（同一题库、同一判据）

优化后连跑 4 次（每次 25 题、真实联网；差异来自 DuckDuckGo 时通时不通）：

| 指标 | 基线 | 优化后（4 次） |
| --- | --- | --- |
| **总分** | **43.1** | **95.1 / 89.1 / 87.5 / 85.3**（均值 ≈89） |
| 空结果率 | 60% | **0% / 0% / 0% / 0%** |
| 判据全中率 | 4% | **96% / 84% / 72% / 72%** |
| 判据基本中率 | 32% | 96% / 96% / 92% / 92% |
| 判据平均覆盖 | 0.237 | **0.973 / 0.933 / 0.890 / 0.890** |
| 期望域名命中率 | 29% | 47% / 47% / 41% / 41% |
| 首条命中率 | 90% | 100% / 100% / 100% / 100% |
| 平均结果数 | 1.16 | 5.72 / 5.48 / 5.36 / 5.44 |
| 平均可信结果数 | 0.76 | 5.28 / 4.64 / 4.16 / 4.20 |
| 来源域名数 | 19 | **91** / 73 / 66 / 68 |
| 延迟 P50 | 2.06s | **0.86s** / 0.93s / 0.83s / 1.01s |
| 延迟 P90 | 2.84s | **2.13s** / 3.73s / 3.79s / 3.42s |
| 链接可打开率 | 85% | 88% / 83% / - / 85% |
| 正文抓取成功率 | 80% | 96% / 96% / 96% / 96% |

**结论：总分 +44~52，空结果率归零，延迟同时下降**（P50 0.83~1.01s vs 2.06s）——
因为不再把预算浪费在"打 4 个必然被拦的引擎"上。最好的一次（95.1）出现在
DuckDuckGo 恢复可用时：判据全中率 96%、平均覆盖 0.973、来源域名 91 个。

> 波动区间 85~95 说明**不要用单次运行下结论**；本报告保留全部 4 次结果。
> 最低的两次（85.3 / 87.5）都发生在 DuckDuckGo 连续失败、英文题只能靠维基补的时段。

| 题目 | 判据 | 原因 |

这些是**搜索源覆盖面的客观限制**，不是代码缺陷；DuckDuckGo 可用时

## 8. 返工（2026-09-21）：上一轮的结论为什么是错的，以及怎么测才可信

### 8.1 上一轮的测量缺陷

上一轮是"先把原始实现跑完一整轮 25 题，再把新实现跑完一整轮 25 题"。
问题在于：**搜索引擎的可用性在这两次之间会变**，而且变得很剧烈。本机实测到的漂移：

| 源 | 某个时段 | 另一个时段 |
| --- | --- | --- |
| `so360` | 25/25 全部正常，且给官方结果（hktdc.com） | 25/25 全部被安全验证拦下 |
| `bing_news` | 25 题里 17 题直接达标 | 25 题**全部返回 0 条** |
| `duckduckgo` | 正常返回 10 条 | 整段时间连不上（每次 16s 超时） |
| `baidu` | 部分查询返回 17 条 | 全程被拦 |

所以"基线 43.1 / 优化后 89"这个对比里，很可能大部分差值来自**引擎可用性**，而不是代码。
更糟的是：原始实现在 so360 可用的时段本来就很好（判据全中 18/25），
而新实现把 so360 排到了最后一批——**在好时段反而用不到它**。

### 8.2 改成交替 A/B

`ab_compare.py` 的做法：对每一道题，**先跑原始实现、紧接着跑新实现**，25 题逐题交替。
这样两边看到的是同一个时间窗口里几乎相同的引擎状态，差值才归因于代码。

结论（25 题、同一时间窗口，累计 7 轮交替 A/B）：

| 轮次 | 更好 | 更差 | 持平 | 覆盖(原→新) | 空(原→新) | 延迟中位(原→新) |
| --- | --- | --- | --- | --- | --- | --- |
| 返工**前**的对照轮 | 1 | **18** | 6 | 0.910 → 0.487 | 0 → 0 | 1.20s → **12.11s** |
| 返工后 6 轮合计 | **37** | 33 | 105 | 0.492 → 0.484 | 7.7 → **3.3** | 7.45s → 7.12s |

- 返工**前**那一轮就是"效果更差"的量化证据：判据覆盖腰斩、延迟涨 10 倍。
- 返工**后**逐题胜负基本打平，但**空结果少了 57%**（同样的上游环境里更少"没查到"）。

### 8.3 返工改了什么（都能对上一条实测证据）

1. **批次顺序按实测重排**：新增 `eval/engine_eval.py` 顺序测量（避免并行猛打把源打爆——
   并行打 8 个源时 so360 被拦 23/25，顺序 + 间隔 0.2s 时 25/25 全通）。结果：
   `so360` 96% 有贡献、`bing_cn` 40%、`bing_web` 36%、`bing_news` 0%、`sogou` 0%、`baidu` 0%（且 25/25 被拦）。
   → 第 1 批 `so360` + `bing_cn`；零贡献的源移到最后。
2. **不再把低于阈值的候选硬塞给模型**：上一版为了"不空手"接受 0.05 分以上的结果，
   实际塞进去的是「2026年放假安排」（搜灯饰展时，0.12 分）。现在只接受 ≥`FALLBACK_MIN`。
3. **恢复"第一批有可信结果就停"**：上一版改成"够 3 条且最高分 ≥0.45 才停"，
   中文题经常一路升级到第 4 批。
4. **修 `count` 失效**：重构时丢了截断，线上按 5 条申请却返回 11~14 条噪声。
5. **被拦的源要冷却**：旧代码对被安全验证拦下的源只记统计不冷却，导致每轮都重复打它，
   把总预算耗光（中位延迟 12s 的主因）。
6. **预算 12s → 8s、请求超时 8s → 5s**。
7. **新增"泛指向页"扣分**：`北京 _ 百科`、`DeepSeek | API Platform` 这类页面
   bigram 命中率天然高却不是答案，会挤掉真正的新闻/定价页。规则用 11 条样例校验，
   刻意保守以免误伤「北京天气」首页、Apple `/iphone/` 落地页。

### 8.4 关于"总分"这个指标的警告

上游整体退化的时段里，本项目的百分制总分只有 57.5/100（基线同条件下更低）。
**这个数字反映的是当时引擎能不能用，不是代码好坏**。判断代码改动只看交替 A/B 的逐题对比。

## 9. 怎么复跑

```powershell
# 完整题库（25 题）+ 链接体检（参数默认对齐线上：count=5、抓 1 篇正文）
py -3 eval/harness.py --all --seed 20260101 --run-name my-run --check-links

# 随机抽 12 题（同 seed 可复现）
py -3 eval/harness.py --seed 20260101 --cases 12 --run-name my-subset

# 【推荐】与原始实现交替 A/B（唯一可靠的跨时间比较方式）
py -3 .bld/ab_compare.py --limit 25

# 按引擎实测贡献度（决定批次顺序）
py -3 eval/engine_eval.py --repeat 1 --gap 0.2

# 和基线对比
py -3 eval/compare.py 05-baseline-full 01-after-optimize 02-verify

# 搜索源健康巡检
py -3 eval/check_engines.py
```
