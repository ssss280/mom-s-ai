# OCR 评测报告

引擎：`qwen3-vl-plus`（配置里的视觉模型）· 题库：17 题合成图 · 调用次数：17

## 结论（一句话）

**17 题全部 CER = 0.0000，含极端模糊、JPEG 质量 15、缩小 50% 的数字题。**

框架是好的，但**这个度量方式对当前模型没有区分度**——合成图测不出它的极限。

**基线：平均 CER 0.0000 · 行命中率 1.0000 · 完全正确 17/17。**

## 为什么全是满分

合成图和真实聊天截图之间差的不是"清晰度"，而是**图像是怎么来的**：

| 合成图（本评测） | 真实截图 |
| --- | --- |
| PIL 用标准 TTF 直接渲染，笔画干净 | 客户端自己的字体引擎，ClearType 子像素渲染带彩边 |
| 纯色背景 | 消息气泡（半透明 / 渐变 / 圆角）、头像、时间戳、状态图标 |
| 整数倍缩放、无重采样 | 非整数倍缩放导致的重采样模糊、屏幕 DPI 缩放 |
| 只有"文字 + 背景"两个元素 | 多元素混排，文字可能压在气泡边缘或图片上 |

也就是说：**模糊和压缩能模拟"画质变差"，模拟不了"布局变复杂"。**
而后者才是 OCR 在真实场景里翻车的地方。

## 这个结论有什么用

1. **OCR 在当前使用方式下不是瓶颈。** 17 题零错误，包括退化到极限的档位——
   与其花精力优化 OCR，不如把时间用在别处。这是一条能省下大量无用功的结论。
2. **它否掉了一个看似合理的做法**：想靠"合成更多更难的图"来测 OCR 极限，是无效的。
   继续加深退化只会继续满分。
3. **要测出差距，必须换度量对象**（见下）。

## 下一步（待定）

| 方案 | 成本 | 说明 |
| --- | --- | --- |
| **真实截图评测** | 中 | 从 `data/screenshots/` 挑真实截图，**人工标注**期望文本。这才是真实分布，但样本含屏幕隐私内容，需要先确认能不能用 |
| 换更弱的引擎做对照 | 低 | 本机**未装 Tesseract**，装一个就能得到"同一批题、两个引擎"的对照——这是最能立刻提高区分度的做法 |
| 接模型 API 的免费替代 | 低 | 用 Ollama 上的本地视觉模型（`llava`）跑同一批题，成本为零且能拉开差距 |

> 三个方案都能立刻产生区分度。推荐**先装 Tesseract 或接本地视觉模型**——
> 零成本、不需要动隐私数据，就能让这套评测第一次真正"量"出东西来。
